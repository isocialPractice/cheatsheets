Generating cheatsheets from another site

A site that already publishes code examples and explanatory sections holds everything a cheatsheet needs; node tools/cheatsheet-site.mjs <site> is what reads it.

It crawls the tree for elements carrying data-cheatsheet, collects what each one wraps, and writes a cheatsheet page per folder of the site that marked any. The output folder is resolved before anything is written - cheatsheets/ under the site root, then cheatsheets/cheatsheets/, then cheatsheets/cheatsheets_0/ and upward until a name is free - so a site that already has one of those keeps it. The script installs nothing, because it runs against somebody else's checkout: every import is a Node builtin or a path inside this repository.

A folder is a subject, so a folder is a cheatsheet

guide/install.html and guide/usage.html are written as guide.html, headed for the folder, with a section per page in the order the site reads them - each keeping the heading it asked for. A page at the site root has no folder to be named for and is written under its own name. Neither the name nor the markup depends on how many pages a folder holds, so the day a second page arrives is not the day the first page's output changes its name. Two folders of one name under different parents, or a root page named for a folder beside it, still want one file in a flat folder: that is reported and the later one is not written, rather than one being overwritten in silence.

The attribute method

The marker's value chooses the page's heading. data-cheatsheet="title" takes it from the page's own <title> and data-cheatsheet="page" from its file name; marked without a value, a page takes its title with its file name behind it. A value naming neither is reported with the page it was written on rather than quietly handed the default, as is an explicit title on a page that has none - the default has a documented fallback and the ask does not.

A heading read off a name is read as prose - somePageName.html is headed Some Page Name, and parseHTMLString.html is Parse HTML String - while a <title> is left exactly as it was written, because a file name is written for a filesystem and a title was written to be read.

The comment method

A page with more than one thing to say marks its material with a comment instead.

<!-- {% cheatsheet: [heading: page, group: page, name: splice] %} -->

It applies to the element that follows it, with nothing but whitespace in between, and carries as many properties as it needs: heading names the source the heading is read from, group says whether the page joins its folder's cheatsheet or is one of its own, and name says what file the cheatsheet is written as. A cheatsheet comment is still a comment, so a marker written inside one is still not a marker.

The two methods side by side

The attributeThe comment
Written on the element wrapping the material on the line in front of that element
Says one thing: where the heading is read from three: the heading source, whether the page joins its folder's cheatsheet, and the file the cheatsheet is written as
To learn nothing - an attribute and one of two values a bracketed list, three property names, and the values each takes
To get wrong a value naming no heading source that, a property the vocabulary does not hold, a property written with no value, one written twice, and a list that is not a list
Reported with the page the page and the line

The trade-off is the first two rows against the next two. An attribute carries one value and there is nothing to get right beyond spelling it, which is why it is the method to reach for first: a page that only wants its material collected says so and is done. A comment carries as much as the page has to say, and the price is a syntax - a list, a vocabulary and a value per property - with five more ways to write it wrong. So the question is not which method is better but how much the page has to say: one thing, and the attribute is the whole answer; a second or a third, and the comment is the only place to put it, because an attribute has nowhere to put a second value.

Nothing is lost by starting with the attribute and moving later. The two feed one collector, a page may use either, a site may use both, and a page changes method by having a comment written in front of the element it already marked.

What happens when they disagree

Where the two speak about one heading the comment wins, because it was written about the material rather than left on an element. The disagreement is reported either way, as is a property the vocabulary does not hold or a value it does not take, with the page and the line it was written on.

The menu, and the page it points at

The third marking is the only one written into a page the site owner keeps rather than read out of it. data-cheatsheet-menu says where the menu goes, and its value says which of the two:

<div data-cheatsheet-menu="page"></div>       a link to the page carrying every cheatsheet
<div data-cheatsheet-menu="dropdown"></div>   an entry per page in the generated folder

Every cheatsheet is also concatenated into all-cheatsheets.html in the generated folder, composed by the same function that writes the individual pages - each cheatsheet is a section of it, with the pages inside a folder's cheatsheet one heading level below, so the two cannot show the same material differently. It is a page of that folder like any other, so it claims its name before any cheatsheet does: a site whose own page wants that name is told rather than written over.

A link is relative to the page it is written into, not to the folder the tool resolved, so a marked page two folders down gets ../../cheatsheets/arrays.html. An entry's text is the prose form of the generated file's name - base64Utils.html reads Base 64 Utils - rather than the cheatsheet's heading, which may have been read off a <title> and be a sentence. The dropdown is a <details> with no class, no style and no script, so it works with JavaScript off and a site that wants its own control has markup to replace.

A menu element is never written over. A fill is wrapped in <!-- cheatsheet-site:menu --> and its closing pair, which is how a run tells its own work from a site owner's: an element carrying that signature is filled again, and one carrying anything else is left exactly as it was. The signature is what makes the refusal possible at all - a menu element is not empty on the second run either, so a refusal that read emptiness would fill once and never again.

Five things are refused rather than written: a value naming neither menu or no value at all, since an attribute carries no default here and guessing writes markup into somebody else's page; an element also carrying data-cheatsheet, or one inside material that is, because filling it would replace the content just read out of it; an element holding such material, or holding a second menu element, since the first would leave the site with no copy of that material at all and the second cut the page's markup apart; an element holding plain content, which is a hand written menu nobody could get back; and a menu on a site that marked no material, which has nothing to list. Each is reported with the page and the line, and the plain content case names both ways out - empty the element, or keep the markup and drop the attribute.

The data file, for a site that is not written yet

Both markings above are written on a page, which is the one thing a site that does not exist yet has not got. A new site, a site generated out of a database, a folder of notes somebody wants a cheatsheet section from before there is anything to publish it beside: each has the material and none of them has a page to mark. So there is a second way in - node tools/cheatsheet-data.mjs <data file> - which reads one JSON file and writes the whole thing: a page per entry, all-cheatsheets.html carrying all of them, cheatsheet-menu.html to move between them, and the manifest.

It is a second front end and not a second generator. A data file says in JSON exactly what a marked up page says in an attribute or a comment, and everything past the read is the same code: the same function renders the pages, plans what a run writes, records the manifest and builds the menu. A cheatsheet generated from a data file and the same cheatsheet generated from marked up pages are the same bytes, which the suite holds by running one piece of material through both routes and comparing the two renders.

The smallest file that writes something:

{
  "entries": [
    {
      "page": "guide/arrays.html",
      "title": "Working with arrays",
      "material": ["<h2>splice</h2><p>Removes and inserts in place.</p>"]
    }
  ]
}

The contract, property by property

This is the mapping, and it is the whole of what a new site writes against. Each property stands for one piece of markup a crawled page would have carried, so a reader who knows one route knows the other.

PropertyTakesIn a crawled site
dataVersion a number nothing - no page declares a version of the markings
menu page or dropdown data-cheatsheet-menu on the element a page wants its menu in
entries a list of entries the pages of the site the scanner crawls
page a path inside the site the page's own path
title text <title>
heading title or page heading: in a comment, or data-cheatsheet="<source>"
group folder or page group: in a comment
name a file name name: in a comment
material a list of blocks the markup a data-cheatsheet element wraps, one block per element

The first three are the file's; the rest are an entry's. An entry is one page, so page and material are the two it cannot be written without, and everything else about a cheatsheet follows from the path the way it follows from a path in a crawled site: a folder is a subject, so two entries named guide/one.html and guide/two.html are written as guide.html, headed for the folder, with a section each in the order they are listed.

A data file is the comment method, said in JSON. That is why heading, group and name are the three a comment carries and not some other set: a comment is the marking that can say several things at once, and so is a record with several fields. The three take their values and their descriptions from the comment's own vocabulary rather than having a second copy of it, so the two cannot be edited into disagreeing.

A block of material

Markup, or a record naming the element it came off:

"material": [
  "<h2>splice</h2><p>Removes and inserts in place.</p>",
  { "tag": "table", "markup": "<table><caption>Returns</caption>...</table>" }
]

Written as markup alone it is recorded as a <section>, which is the preset half of the mapping: a crawled page has an element whether or not it meant to choose one, and a data file has none, so one is supplied. The name is written onto the generated page as data-cheatsheet-block - the same place the scanner records the real element it found - and is read by nothing else, so naming it is worth doing only where the element says something about the material.

The menu is a page here

A crawled site has pages of its own for a menu to be spliced into, and a data file site is nothing but the generated folder - so the menu is a page of that folder. cheatsheet-menu.html is the front door: the same <details> a marked page would have been filled with, in the same document shell every generated page carries, linking its siblings. It is written only where the file asks for a menu, and it claims its name the way all-cheatsheets.html does - an entry that wants it is told rather than written over.

What a file can be wrong about

The same judgement the markings get: a property the contract does not hold, or a value it does not take, is reported and ignored, and the pages that could be read are still written. A finding names the property's path in the file - entries[2].heading - because that is what a reader has to go and edit. An entry that names no page, names a path outside the site, names a page another entry already stands for, or carries no material is reported and writes nothing; a file that is not a record, holds no entries, or declares a version this tool does not read is refused whole, because a file written against a later vocabulary holds properties this one would drop in silence.

node tools/cheatsheet-data.mjs --help prints the table above from the same object the read uses, so the two cannot come apart.

What a generated page carries

A render of a cheatsheet document, and the material it was read from. The collected blocks become a document of the three models, that document is composed through the output surface, and the composed sheet is embedded at the top of the page - so a media file of the same cheatsheet is another render of the same object rather than a second code path that happens to agree today.

<h1>Acme Reference</h1>
<div class="cheatsheet" role="img" aria-label="Acme Reference cheat sheet">
  <svg id="cheatsheet-site-index" viewBox="0 0 3600 3600">...</svg>
</div>
<main data-cheatsheet-block="section">...the site's own markup...</main>

The markup stays because the reading is lossy and a sheet is a picture of text: a table becomes rows, a chart's <script> contributes nothing, and a <pre> listing loses its indentation. A reader who wants the table rather than a picture of it has nowhere else to get it, so the figure is the reading and the markup underneath is the record. A heading, a caption and a table's header cell keep their role as the comment rows a label is set in; material that reads as no text at all - a page of nothing but an <img> - gets no figure rather than a sheet with an invented row on it.

Two things in the markup do not survive untouched. The first is a relative URL, and it is the one that could not: a relative URL is relative to the page it was written on, and a generated page sits in another folder - so <img src="badge.svg"> on guide/using-it.html would ask for cheatsheets/badge.svg and get nothing. Every relative src, href, srcset and poster in carried material is therefore rewritten to point from where the generated page sits at what it pointed at:

guide/using-it.html    <img src="badge.svg">
cheatsheets/guide.html <img src="../guide/badge.svg">

Nothing else is changed. An absolute URL, a protocol relative //host one, a path that was already root relative, and a bare fragment all already mean what they meant, so all four are carried as written - and a path that walked above the site root was leaving the site anyway and has no site relative form to rewrite into. Two attributes are left alone on purpose: rewriting a <form action> would point a form at a handler nobody expected, and rewriting a <base href> would change how every other URL on the page resolves rather than one of them. The query and the fragment on a rewritten URL ride along untouched, a path naming a folder keeps its trailing separator, and a URL inside a comment or in what a carried <script> says is text rather than markup and is not touched. A bare ?query with no path meant the page it was written on and now means the page carrying it, which is the one shape still carried as written. If you pass --out a folder outside the site there is no relative path from the generated page to anything, so the URLs are carried as written and the run says which page and how many.

The browser route does none of this, and should not: it builds its section inside the page that is already loaded, so a relative URL in the material is already relative to the right page.

The second is a carried table, which is written inside a <div> the tool owns. It is the box the table scrolls in, and it is also the one element on the page that can carry the keyboard attributes a scrolling box needs - both of which are the next section. Nothing about the table itself is changed: it is handed across as you wrote it, inside a wrapper that was not there before.

<div data-cheatsheet-scroll tabindex="0" role="region" aria-label="Regions and their quarters">
<table>...</table>
</div>

data-cheatsheet-scroll is not a marking and cannot be read as one, which is what makes it safe to write into a folder the next run walks over: the scanner requires the character after data-cheatsheet to end the attribute name, so a longer name is a different attribute. The browser route writes no wrapper, because it has no style block to pair one with - it builds its section inside a page that already carries your stylesheet.

And four rules about its own layout, written into the head as a <style> block with a comment above it saying what it is for:

<style>
[data-cheatsheet-block] pre { overflow-x: auto; }
[data-cheatsheet-block] img { max-width: 100%; }
[data-cheatsheet-block] [data-cheatsheet-scroll] { max-width: 100%; overflow-x: auto; }
[data-cheatsheet-block] table { max-width: 100%; }
</style>

A generated page is written whole and carries no stylesheet, so a <pre> on it is white-space: pre and overflow-x: visible by the browser's own default - and one long line anywhere in the carried material then sets the width of the whole document, which is a page that scrolls sideways on a phone. The listing scrolls itself instead, which is what docs.css chose for these pages; wrapping it was the alternative and it would change what a listing says, and the material underneath the figure is the record. Every selector is scoped to data-cheatsheet-block, so the rules reach the blocks the tool wrote and nothing else in the folder, and anything added after them wins on cascade order. There is nothing here about type, colour or spacing, and nothing about the figure, which carries its own inline style and needs no second opinion.

The table rule is the listing rule and not the image one, which is the distinction worth knowing if you are reading the block and wondering why a table needs a wrapper at all. An <img> arrives with an intrinsic width, so clamping it to the page is the whole answer. A table is wide because of what is in it - its used width is never lower than the sum of each column's longest unbreakable run, and max-width does not lower that - so a table with enough columns is wider than a phone whatever the clamp says. It needs a box that overflow-x reaches, and a display: table box is not one. The alternative that also contains it, table-layout: fixed with width: 100%, reflows every column to an equal share - and the material under the figure is the record, so scrolling it is preferred to re-laying it out, for the same reason wrapping a listing was refused above.

The box is the wrapper and not the table, and the reason is a declared width. Between 2026.11.11 and 2026.11.13 the rule put display: block on the <table> itself, which contains it - and takes it out of the table formatting context, so its <caption>, <thead> and <tbody> are wrapped in an anonymous table box that has no width of its own and shrinks to fit. A width you declared on the table then sized the block that scrolled rather than the table that laid out, and your columns were laid out as though you had declared nothing. Measured on a generated page at 1280px, a <table style="width: 100%"> was a 1264px box with its rows drawn at 152.9px; with the style block removed the same rows took 1258. A table that declared nothing was untouched either way. width: 100% is the commonest thing there is to write on a table, so that reached ordinary pages. The containment is on a wrapper now, the table is a table box again, and a width you declare lays out columns again.

A table of your own that you would rather not have in a scrolling box is a rule written after this block, which wins on cascade order: [data-cheatsheet-scroll] { overflow-x: visible }.

The wrapper carries tabindex="0"; your listing still carries nothing. A scrollable region with no focusable child inside it is reachable from a keyboard only where the browser makes scroll containers focusable itself, which was taken on trust until it was measured on 2026.11.12 at 390x844, on a generated page carrying a table 2586px wide in a 374px column and a wide listing:

Chromium 151              both boxes in the tab order, 40px per ArrowRight
Firefox 153               both boxes, 32px and 36px per press
WebKit 605.1.15 (Safari)  neither box in fourteen presses

So two engines of three reach it and one does not, which left carried material that overflows unreachable without a pointer on Safari. The remedy - tabindex="0" with an accessible name - was refused for being two things the tool cannot do: an attribute written into your own element, and a name invented for material it only read. Neither reaches the wrapper. It is the tool's own element, and a table's <caption> is your words rather than an invented name, so the wrapper carries tabindex="0", with role="region" and an aria-label from the caption where there is one. A table with no caption is still reachable and claims no role, because a region a screen reader announces and cannot name is worse than no region at all.

And the engine that needed it is now the engine it is measured in. Until 2026.11.14 the suite drove Chromium, which is one of the two that never needed the attribute, so the reading the whole remedy rests on was the one nothing asserted. tools/test-site-pages-browser.mjs now runs the cases that measure containment and keyboard reach over whichever of Chromium, Firefox and WebKit are installed, and skips per engine with the install command where one is not.

Both objections still stand for a listing, which is why it is left as it was: a <pre> is your own element and has no caption to be named from, so the only remedies are an attribute written into your markup or a wrapper under a name the tool made up. On Safari, a carried listing wider than the page cannot be scrolled from a keyboard. If that matters on your site, you have the two levers that always win here: your own CSS after this block, and your own markup, which the tool carries rather than rewrites - a tabindex="0" on the <pre> in the page you keep is carried onto the generated one with everything else.

The one cost of the attribute is a tab stop that may do nothing, since whether a box overflows is a layout result and not something a generated file knows: it is written on every carried table's wrapper rather than on the ones that scroll. That is the trade - an extra stop on a <div> the tool wrote is a smaller cost than material no keyboard can reach.

max-width: 100% on the table is the whole of what is left on it, and width: fit-content is gone with the block box that needed it. A table box shrinks to fit on its own; it was a block box that filled its container. Two carried tables that measure 439 and 512 wide at 1280px measure 439 and 512 with this block, which is what they measured before any of it existed, and only a table wider than its box is contained.

Every fragment is named, because the master page holds one per cheatsheet and a composition carries id="cheatsheet" on its root. The name is the generated file's stem, which the flat output folder has already made unique, slugged the way the surface slugs a render's file name - a stem is a site owner's own file or folder name, and an id may hold no whitespace.

The browser route, for a site with no build step

The scanner reads files, so a marker a script wrote at run time is invisible to it. api/cheatsheet/site.mjs is the other half, and it needs no checkout, no Node and nothing installed - a page that can run a module can build its own cheatsheet section from the elements it already has:

<script type="module">
  import { cheatsheetSection } from "./api/cheatsheet/index.mjs";

  const { element, findings } = cheatsheetSection(document);
  if (element) document.querySelector("#cheatsheet").append(element);
  for (const finding of findings) console.warn(finding);
</script>

It reads the same two markings, because the attribute names, the heading sources and the element lists are declared there and the scripted tool imports them: one vocabulary with two readers rather than two that agree until one is edited. The section it builds is the shape the scripted tool writes - a heading, the composed figure, and a <main> per block - so a site can move between the routes without its stylesheet changing. It carries no <style> block of its own, because the section is appended to a page that already has a stylesheet: a site that wants the listing rule on that route writes the one above into its own CSS, where it can be read and changed. The material is cloned rather than moved, and the section is handed back rather than inserted, since where it goes is the page's decision.

Two things it does not do. There is no generated folder, so a data-cheatsheet-menu on the page is reported rather than filled: a menu pointing at pages nobody wrote is worse than no menu. And nothing is written to a file and nothing is fetched - it reaches the document it was handed and the modules beside it, which is what lets it load from a page with no bundler.

Reading a run before trusting it

A run can be read before it is trusted and run twice without moving anything. --dry-run reports the folder it resolved and the pages it would write, and touches nothing. A real run records the name it resolved in cheatsheets/.../cheatsheet-site.json, and a later run reads that rather than resolving a second section beside the first - which is what it would otherwise do, because run one's output is what makes cheatsheets/ taken for run two.

The manifest carries no timestamp, so a second run over an unchanged site writes the same bytes and the generated pages can be committed and diffed. It records its own shape, and a run reads every shape the tool has written: the folder is read off where the file sits rather than out of the file, so an older manifest answers that as well as a current one and is rewritten on the way past.

There are two sites to run it against, committed. fixtures/site/ is a small placeholder site - half tutorial, half tool documentation - carrying every page shape the tooling has to handle: prose sections, code examples, a table, and a chart whose script holds a </div> in a string, which is the case that proves a script is an opaque span rather than markup. It carries every marking as well: the attribute on four of its six pages, the comment syntax on a fifth, both menu modes, and a folder inside a folder, so that the name a cheatsheet takes is read off the immediate parent rather than assumed. fixtures/site-taken/ is the second root, where everything is already the site owner's - a cheatsheets/ folder the output ladder resolves past, and a hand written menu a run refuses rather than writing over. Read their READMEs for what is in each: site and site-taken.

node tools/cheatsheet-site.mjs fixtures/site --dry-run

What a run writes against either one is committed too, under fixtures/expected/: every file it creates or changes, at the path it lands at, including the pages whose menus were filled. tools/test-fixture-expected.mjs runs the tool against a copy and compares the two, and the Pages workflow runs it before it publishes - so a change that moved a generated page is a diff to read rather than something that reaches a site unnoticed. The <svg> in those pages is the API composing material read off the fixture, so that comparison holds both halves of the tooling at once.

Why the collector is a scanner

Having no parser available is what makes the collector a scanner, and the limits of scanning are listed in that file's own header rather than left to be discovered. A start tag is walked rather than searched, so a > inside an attribute value is not read as the end of one: <div title="a>b" data-cheatsheet> is legal HTML, is one element, and is collected as one.
