Rendering a sheet outside the page

The page composes its sheet as SVG in the browser and nothing commits a raster, so a picture of a sheet is made on demand.

node tools/cheatsheet.mjs --generate <slug> --format webp

It composes and renders through the same layer the page does, which then takes one of two routes - a real engine, which draws the face the design language measured, or the drawing surface's own dependency free rasterizer, which draws a built in single stroke alphabet. It reports which one answered, because a file that does not say that cannot be reviewed against the design language.

The flags

FlagWhat it does
--theme, --layout Each takes the one name the record supports or a path to a JSON model of its own. A --theme file may be partial.
--data-only Emits the document and what the composition chose without rendering anything.
--list Names what there is.
--document <path> Reads a JSON document from anywhere in place of a slug.
--all Every cheatsheet in the catalog, each from its own sheet.json.
--help The rest.

The whole catalog is one act

--generate has composed a sheet through this layer since the day the command existed, and --check has read every committed document since the same day - but there was no way to write all of them, so the answer to "how is a new cheatsheet's picture produced" was one invocation per sheet, or a screenshot taken by hand. For a catalog growing from one category to ten, that figure is what decides the cost of writing one sheet.

node tools/cheatsheet.mjs --all

It composes each entry by the same path a single --generate takes, so a batch and one slug write the same bytes to the same place - a loop that rendered its own way would be a second command that agrees until one of them is edited. A sheet that cannot be composed is reported against its own id and the rest still run, the exit code saying some failed: somebody fixing one sheet.json should not have to wait for the rest of the catalog.

--out, --seed and --data-only are refused with it rather than ranked, because each means one sheet - one destination, one document's variation, one document emitted - and a batch has one of each per cheatsheet. Nothing a batch writes is committed: the page composes its own sheet in the browser, so a render is on demand here as it is anywhere else.

A sheet does not have to be in the catalog

--document <path> reads a JSON document from anywhere in place of a slug, so the command is an entry point for a document rather than for this repository's own index. It reports the same fields either way, with source saying which flag named the sheet.

Only markup carries the footer's links

A sheet's footer links out - see Drawing a sheet for what links where - and whether a render can carry those links depends on its format.

FormatThe links
svg Written into the markup as a final <g data-name="links">, which a browser opening the file follows. Take that group off and what is left is the composition's own markup, byte for byte.
html Lifted out of the picture into a <nav> laid over it, because everything inside role="img" is presentational and a link there would have no name a screen reader can give.
png, jpeg, webp None. A raster is drawn from the composition, not from the markup, so its bytes are the same whatever the links say. A page that shows one puts the links beside it.
