Configuration

Where the options are read from

config/reports.json beside the records folder, where there is one. Every option has a default, so a folder with no configuration file is a folder that reads with the defaults rather than one that refuses.

Options
OptionDefaultWhat it decides
folder./recordsWhich folder is read
schema./schema.jsonWhich fields a record must carry
outputDir./reportsWhere a written report lands
strictfalseWhether a field the schema does not name is a failure
localeenHow a date in a record is read

The one option worth setting deliberately

strict decides what an unknown field means. Left off, a record may carry anything the schema does not name; turned on, it may not - which is what a folder that several tools write into wants, and what a folder a person maintains by hand almost never does.

Reference

Commands

check

Reads the folder and reports. Writes nothing.

demo-app check [folder] [--quiet] [--json]

write

The same read, with the report written to outputDir. The file is named for the day it was written, so a second run on one day replaces that day's report rather than growing a folder of them. 

demo-app write ./records --out ./reports

explain

Takes one record and says what the check made of it, field by field. It is the command for the failure nobody can reproduce from the report alone. 

demo-app explain ./records/0042.json

What every command refuses

A folder that is not there, and a schema that names a type the tool has no reader for. Both are reported with the path rather than the sentence, so there is somewhere to go and look. 

demo-app check ./missing
# demo-app: ./missing is not there.

Exit Codes

The three codes

0
Every record carried every field the schema declares.
1
The folder was read and something in it failed the check.
2
Nothing was read: the folder or the schema is not there.

Why a failed check is not an error

A record that failed is an answer, and the report names the field it failed on. A folder that is not there is a question nobody can answer, which is the one case worth telling apart in a scheduled run. 

demo-app check ./records --quiet
echo $?

Reading one without reading the report

The code says whether to look. The report says where, so a run that only branches on the code is a run that still has to read it afterwards. 

demo-app check ./records || demo-app explain ./records/0042.json

Acme Corp Handbook

What demo-app does

demo-app reads a folder of records, checks each against the schema it declares, and writes a report. It installs nothing and reads nothing but the folder it is pointed at.

The three words worth knowing

Record
One file in the folder, holding one subject.
Schema
The fields a record must carry, and what each one may hold.
Report
What came back: the records that passed, and the field that failed on each that did not.

Where to go next

Start with the tutorial if you have a folder of records already. Read the configuration pages first if you are deciding whether the schema can say what your records need.

Tutorial

Getting Started

Check one folder

One argument, and the folder is read in place. Nothing is written.

demo-app check ./records

Declare what a record must carry

A schema is a plain object. Every field names a type, and a field left out of the schema is a field the check ignores. 

const schema = {
  id: "string",
  opened: "date",
  owner: "email",
  total: "number",
};

Read the report rather than the exit code

The exit code says whether anything failed. The report says what, which is the half worth reading in a terminal. 

const report = await check("./records", schema);
for (const failure of report.failures) {
  console.log(`${failure.record}: ${failure.field} ${failure.why}`);
}

Two flags, and when each is worth it

--quiet prints the failures and nothing else, which is what a scheduled run wants. --json prints the report as data, for anything that reads it rather than looks at it. 

demo-app check ./records --quiet
demo-app check ./records --json > report.json
